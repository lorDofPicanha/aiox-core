Visão geral

Um cérebro distribuído, não um único modelo

O AIOS trata cada CLI de IA como um órgão especializado de um mesmo organismo. Em vez de depender de um provedor, ele roteia cada tarefa para a ferramenta que faz aquilo melhor — e mais barato — usando uma camada de delegação universal.

Toda a coordenação acontece sobre dois alicerces que existem em qualquer ambiente: o terminal e o filesystem. Não há daemon, servidor novo, nem handshake. O estado da verdade vive em arquivos versionados; os modelos apenas leem e escrevem nesse estado.

Decisão de fundação

Por que não usar MCP como espinha dorsal

O MCP (Model Context Protocol) é poderoso, mas frágil como backbone. Na prática ele quebrou caminhos críticos — o que motivou a escolha por uma bridge CLI.

Problema observado no MCPEvidência real
Handshake falhaplaywright + nano-banana-2 quebraram no Codex 0.131
Quebra o IDE inteirojarvis MCP inutilizou o Antigravity
Regex de nome rejeita@21st-dev/magic rejeitado
Version mismatchgpt-5.5 exigiu upgrade; SDK 0.116 incompatível
Stdio frágilrmcp transport: serde error em runtime
💡

Insight central: o aios-brain-bridge sempre foi apenas um wrapper sobre arquivos em D:/jarvis/bridge-data. O MCP é uma porta opcional — e a mais frágil. A regra de ouro: nunca dependa de MCP para um caminho crítico. CLI é o fallback que sempre funciona.

A cola

O roteador delegate.js

Um único comando despacha trabalho para qualquer cérebro. Os mesmos flags (--model, --sandbox, --json) são traduzidos para o vocabulário nativo de cada CLI.

# Execução bulk no Codex (billing OpenAI)
node .aios-core/infrastructure/scripts/delegate.js --to codex "refatore X nestes arquivos"

# Classificação barata no Gemini (Flash; seleciona modelo por agente)
node .aios-core/infrastructure/scripts/delegate.js --to gemini --agent architect "avalie este tradeoff"

# Conselho de mind clones (jarvis, file-based)
node .aios-core/infrastructure/scripts/delegate.js --to jarvis --topic "pricing" --limit 3

⚠️

A rota --to gemini está implementada e validada, mas a execução ponta-a-ponta exige auth do Gemini CLI (GEMINI_API_KEY ou Vertex/GCA). O CLI retorna exit 0 mesmo sem auth, então o roteador inclui um guard que avisa antes de gastar a chamada.

Orquestração multi-nível

Cadeias master → chief → clone

O grande risco da migração era o limite agents.max_depth=1 do Codex, que quebraria orquestrações aninhadas. Resolvido — e com uma nuance arquitetural elegante.

NívelMecanismoStatus
1 → 2  aios-master → chiefSubagent nesting (max_depth=2)PASS · T1
Paralelismomax_threads=8PASS · T5
3 → chief → mind clonetool call via brain-bridge — não consome profundidadePASS · T2
Workflow encadeado@sm → @architect → @qa → @devPASS · T10
🎯

Por que max_depth=2 basta: o 3º nível (consulta ao mind clone) é uma chamada de ferramenta via brain-bridge, não um subagent aninhado. A profundidade de subagent fica em 2 e a cadeia funciona ponta-a-ponta.
