Cockpit de Orquestração Multi-Agente CLI

Plataforma única conectando Claude Code + Codex + Gemini/Antigravity, com chat-orquestrador (jarvis), observabilidade em tempo real, relatórios consolidados e fila de tarefas.

Solicitante: Breno Cerqueira (AIOS) · Data: 2026-05-20 · Método: tech-research skill (6 fases) · Dimensões: Técnico-arquitetural + Mercado · Confiança: Alta (3 frentes paralelas, fontes trianguladas)

Sumário Executivo

Pergunta real: Devo construir, adotar (fork) ou adiar um cockpit que une as 3 CLIs sob o jarvis — e qual arquitetura, dado (a) a Constituição CLI-First do AIOS, (b) o split de billing da Anthropic em 15/Jun, e (c) o custo de oportunidade vs Anipis (beta 30/Mai)?

Recomendação: BUILD LIGHT (Nível A) + BUY na execução — construir um cockpit de OBSERVABILIDADE leve (Next.js lendo D:/jarvis/bridge-data/ + chat jarvis + custo via ccusage), e NÃO construir orquestrador de execução. Para rodar agentes em paralelo, adotar Emdash (ou Vibe Kanban) quando isso virar necessidade real. Timebox: MVP de fim de semana, depois do beta do Anipis.

3 justificativas

  1. O tool exato não existe como OSS maduro. Nenhum projeto reúne os 5 pilares (multi-provider + chat-orquestrador + observabilidade + relatórios + fila). Você montaria de peças — então build-light dirigido é mais barato que forçar um fork inadequado.
  2. A Constituição CLI-First já decide metade. "Dashboards apenas observam, nunca controlam." O Nível A (observar) é constitucional e zero-conflito; o Nível C (auto-orquestrar) fura o Artigo I.
  3. O substrato já está pronto. O jarvis já escreve eventos/relatórios em bridge-data/. O cockpit de observação é majoritariamente uma camada de leitura — esforço baixo, stack que você já domina (Next.js).

3 riscos

  1. Billing trap (CONFIRMADO): auto-dirigir Claude via claude -p cai no pool separado caro pós-15/Jun. Mitigação: cockpit observa; execução fica nas sessões interativas / Codex.
  2. Custo de oportunidade: Anipis beta está a ~10 dias. Construir agora atrasa o que paga a conta. Mitigação: adiar para pós-beta.
  3. Windows gap: quase todo OSS assume tmux/Linux. Embarcar sessões vivas exige trabalho ConPTY custom. Mitigação: começar só-observação (não precisa de PTY embutido).

1. Contexto e escopo

O que está em jogo: a visão de um "cérebro central operável" — você conversa com o jarvis num painel, ele orquestra as 3 CLIs, você vê o que cada agente faz e recebe relatórios consolidados. Decisão de alto valor (semanas de build potencial).

Restrições não-negociáveis:

  • Constituição CLI-First Artigo I — dashboards observam, não controlam; UI nunca é requisito de operação.
  • Billing pós-15/Jun — uso programmatic (Agent SDK / claude -p) mete em pool separado pago a rates de API.
  • Windows — ambiente nativo, sem WSL como requisito.
  • Estado em arquivos — jarvis já é file-based em D:/jarvis/bridge-data/.
  • Oportunidade — Anipis beta 30/Mai tem precedência declarada.

Investigado: landscape OSS de orquestradores multi-CLI, padrões de arquitetura (worktrees, PTY, headless, observabilidade, orquestração, estado), tooling de observabilidade/custo. Não investigado: dimensão regulatória (irrelevante) e científica (n/a).

3. Shortlist — 5 mais próximos do seu caso

1Emdash — melhor aposta multi-provider viva. ~22 providers, UI desktop, visibilidade real-time de worktrees, YC W26, shipping diário, Apache-2.0. Gaps: sem relatórios consolidados, sem chat-orquestrador, sem coordenação entre agentes — mas a base mais limpa pra forkar/estender.

2Composio AO — orquestrador autônomo mais forte: dashboard web, kanban por estado de CI, auto merge-conflict/CI/review, muito ativo. Perde: sem Gemini; ineficiência ociosa entre passos.

3Vibe Kanban — mais completo no papel (kanban + 10 providers + observabilidade web + MCP), ecossistema enorme. Mas Bloop fechou — manutenção comunitária. Adotar só se for co-manter.

4CliDeck — o único com chat-orquestrador genuíno (estilo WhatsApp) sobre CC/Codex/Gemini + autopilot + controle mobile. Ressalva: 77★, novíssimo, não-provado. Vale vigiar.

5Bernstein — escolha se "relatórios consolidados" = auditabilidade: logs HMAC encadeados, lineage por artefato, scheduling determinístico, 40+ adapters. Sem GUI/chat, é um backend que você embrulha.

Fronteira não resolvida: múltiplas comparações de 2026 concluem independentemente que coordenação entre agentes contra um plano compartilhado é o problema em aberto do OSS — preenchido só por tools comerciais (Conductor, Intent, Tonkotsu, Cursor parallel agents). Ninguém OSS combina chat-orquestrador + multi-provider + relatórios + fila + visão ao vivo.

4. Padrões de arquitetura (como esses sistemas são feitos)

Git Worktree Isolation

Cada agente num diretório/branch próprio, mesmo .git. Edição paralela sem colisão; merge no nível de branch. Universal — todo tool converge nisso.

Falha: conflitos quando 2 agentes tocam o mesmo arquivo; duplicação de node_modules; portas/DB colidem sem partição.

Terminal Multiplexing

(a) tmux→browser via xterm.js (Webmux, agentboard); (b) node-pty direto sobre WebSocket. Vibe Kanban nem embute TUI — spawna child process e captura stdout.

Falha: xterm renderiza bytes, não eventos estruturados; tmux é segunda-classe no Windows.

Headless / Programmatic

claude -p / codex exec / gemini -p com stream-json. Mas os dashboards de worktree embutem sessões interativas, não -p — por visibilidade E billing.

Falha: headless perde skills/slash-commands interativos; -p dispara billing programmatic.

Event Streaming / Observabilidade

(a) Hooks Pre/PostToolUse → arquivo/socket; (b) parse do stream-json; (c) OpenTelemetry (CLAUDE_CODE_ENABLE_TELEMETRY=1).

Falha: dashboards xterm-only não têm telemetria estruturada; OTel exige collector rodando.

Orquestração

Supervisor/worker ou swarm/handoff. Crítico: os dashboards CLI NÃO usam LangGraph/CrewAI — orquestram via kanban/fila + worktrees + subprocess. Frameworks orquestram chamadas LLM (e roteiam por API key = 2ª conta).

Falha: fila perde contexto compartilhado; framework adiciona runtime pesado + 2º billing.

Estado Compartilhado

Modelo de referência (Vibe Kanban): estado de código = Git (worktrees); estado de workflow = SQLite. Coordenação runtime via daemon MCP que distribui portas. Webmux deriva tudo de worktrees+tmux.

Falha: sem fonte única se misturar DB+git+tmux; contenção de portas sem broker.

5. A armadilha de billing CONFIRMADA

Fonte primária Anthropic (Help Center + docs): um dashboard que auto-dirige Claude via claude -p passa pelo Agent SDK e é cobrado separado pós-15/Jun — saca de um crédito mensal próprio ($20 Pro / $100 Max-5x / $200 Max-20x, USD, rates de API, sem rollover). Claude Code interativo no terminal/IDE continua no pool de subscription, inalterado.

O gatilho é a superfície -p/SDK (+ GitHub Actions + apps third-party autenticando via sua subscription) — não "ausência de humano". Por isso um cockpit consciente de custo deve embutir sessões interativas, não bombear claude -p.

7. Síntese dialética — Build vs Buy

TESE (Buy/Fork) Adotar Emdash ou Vibe Kanban. Já implementam ~80% de execução+fila+worktrees. Forkar evita green-field. Vibe Kanban tem o modelo de estado de referência (Git+SQLite); Emdash está vivo e cobre os 3 providers.

ANTÍTESE (Build) Nenhum casa com a combinação específica. multi-provider + chat-conductor + cérebro jarvis + estado-em-arquivo + Windows nativo + billing-safe + constitucional. Todo fork exigiria trabalho pesado: ConPTY Windows, integração jarvis, camada de chat. E são execução-céntricos (dirigem agentes) — atrito direto com "observar, não controlar". Vibe Kanban ainda tem risco de sunset.

SÍNTESE Duas camadas, decisões separadas:

  • Camada 1 — Observabilidade (BUILD light): Next.js lendo bridge-data/ + chat jarvis (voz Gemini/Codex) + custo via ccusage + feed de atividade no padrão disler. Constitucional, billing-safe, ~1 semana, stack que você domina. → Esta é a recomendação imediata.
  • Camada 2 — Execução (BUY quando precisar): se um dia quiser que o painel lance agentes em paralelo, adote Emdash como superfície de execução em vez de construir gestão de worktree. Mas isso é Nível B/C e cruza a linha de controle — decidir depois.

Condição de validade: válida enquanto (a) você opera as 3 CLIs manualmente e quer só visão+conselho; reavaliar se (b) execução paralela massiva virar necessidade diária, ou (c) surgir um OSS que feche os 5 pilares.

Stack mínima (zero infra pesada)

  • Captura: hooks das 3 CLIs anexam eventos JSON em bridge-data/ — você já faz.
  • Watch + stream: Route Handler Next.js roda chokidar na pasta → push via SSE pro cliente (feed "agente X fazendo Z").
  • UI: shadcn/ui shell + Tremor charts; timeline do event log.
  • Custo: ccusage parseia os JSONL de Claude/Codex/Gemini → cards de spend por provider; refresh on file change.
  • Relatórios: módulo pequeno que agrega event files por sessão num digest (arquivos mudados, comandos, decisões, custo).
  • Chat jarvis: painel que roda self-consultation.js via CLI; voz = Gemini/Codex (barato). Orquestra propondo, você aprova, execução vai pra CLI real / delegate.js.

Princípio: o cockpit observa (lê arquivos = grátis) e aconselha (chat jarvis voz barata). Execução pesada continua na CLI real (billing como já desenhado). Zero ClickHouse/Redis/Postgres. 100% local, multi-provider, constitucional.
